# Massive Improvement Wave 2 — Tiferes Execution Plan

> Tiferes joins many lanes without letting one race trample another file beneath its feet;  
> Awtsmoos.com keeps the work parallel in discovery, serialized where writes overlap, and verified before each mission is complete.

## Parallel Discovery Lanes
A. Resource history + portable serialization current-state reconciliation.
B. Full test baseline and first failing test capture.
C. Source lifecycle/Stage mutation-island map.
D. Deployment config/git remote/static hosting archaeology.
E. Public Awtsmoos.com route discovery and HTTP verification.
F. Isolated server/Chrome port readiness and browser ownership.
G. Structural/dependency/compressed-code scan.
H. Lazy feature idempotency/projection lifecycle audit.

## Write Order
1. Portable serialization + runtime resource ledger/history fidelity.
2. Source duplicate/move/remove commandization only after resource lifecycle is proven.
3. Stage drag/selection command parity.
4. Highest-risk compressed runtime module split discovered by scans.
5. Lazy idempotency fixes if evidence finds duplicate binding.
6. Deployment/preview config only if platform contract is discovered and safe.

## Verification Order
Focused tests → source/history regression → whole Studio tests → static checks → isolated desktop browser → isolated mobile browser → public URL verification → reread/delta/git review.

## Deployment Gate
A URL is called `deployed` only if project/platform evidence proves it is a persistent public route. If only a tunnel preview is available, label it `public preview`. Verify any returned URL with an actual HTTP/browser request before reporting it.
