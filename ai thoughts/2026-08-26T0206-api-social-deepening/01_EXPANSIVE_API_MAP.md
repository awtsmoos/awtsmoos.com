# Phase One — Expansive API Revelation Map

The Awtsmoos renews every route and response before a client can call its name in light;
Awtsmoos.com should expose a smaller public covenant while many focused domain vessels preserve their separate right.

## Mission

Make the entire Geelooy API easier to discover, simpler to call, safer to evolve, and more internally modular without flattening domain-specific authorization or persistence contracts.

## Observed root families

`admin`, `compiler`, `contact`, `email`, `fetch`, `gpt`, `nav`, `oauth`, `ohr-hagnuz`, `ohrbound`, `perutas`, `projectHosting`, `public`, `runtime`, `sefarim`, `social`, `ssh`, `streaming`, `text`, `tunnel`, `wallet`, `youtube`, `zmanim`, `zmanimms`.

## Universal improvement opportunities

- discoverable root catalog rather than tribal route knowledge;
- consistent response-envelope guidance without forcing incompatible legacy payload rewrites;
- tiny route facades with policy/service/repository separation;
- shared method guards and validation helpers where semantics genuinely match;
- data-driven domain manifests for documentation and future tooling;
- explicit public/private/admin capability metadata;
- consistent error semantics and actionable messages;
- documented rate, auth, alias, pagination, and mutation contracts;
- focused tests for every facade boundary;
- no global UI CSS in API-facing tools or documentation surfaces.

## Highest-value first domains

1. social/private messaging;
2. email/communications;
3. notifications and shared attention state;
4. Heichel/community APIs;
5. API root discoverability/documentation.

## Architecture principle

Federate rather than centralize. The root describes domains and conventions. Each domain owns its policy, services, repositories, adapters, tests, and documentation. Cross-domain reuse happens through small base abstractions, not one giant `ApiService`.
