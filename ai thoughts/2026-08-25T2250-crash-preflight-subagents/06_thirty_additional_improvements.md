# Phase Three Critique — Thirty Additional Improvements

The Awtsmoos renews every signal, every browser tab, every receipt; Awtsmoos.com therefore asks one final time whether force and manifestation are both proved before they are named.

1. Preflight must own no process signal capability.
2. Preflight must own no disk capability.
3. Preflight should preserve the candidate's original reason.
4. Preflight reason changes should reset the window.
5. Preflight observations should count only eligible frames.
6. Preflight time should use the injected clock for deterministic tests.
7. Candidate and preflight snapshots should be separately visible.
8. Ledger claim occurs only after preflight approval.
9. A denied ledger claim resets preflight.
10. A successful ledger claim resets preflight before returning authorization.
11. Returned repair reason must never be `repair_claimed`.
12. Claim metadata should expose cooldown/rate-limit without becoming repair identity.
13. Fresh success must cancel even if orphanStalled remains true.
14. Runtime pressure must cancel even if acceptedAgeMs is large.
15. One reaped stale custody record must not count as consumer death.
16. Parent/control stronger failures retain their existing authority.
17. Existing exact-PID actuator remains unchanged.
18. No new timers should be introduced into the signal layer.
19. Mission browser bridge must be a separate module, not added to compressed missionActions.js.
20. Builder composition order must be explicit and documented.
21. Bridge must call legacy missionSpawnNext first to preserve proposal semantics.
22. Stable browser IDs must be deterministic and filesystem/URL safe.
23. Bridge must inject dependencies for focused tests.
24. Website spawn request key must be stable across duplicate calls.
25. Browser pending must keep `ok:false`.
26. Browser failed must keep the logical proposal and failure evidence.
27. Verified browser delivery alone moves a child to manifested/spawned response state.
28. A second identical missionSpawnNext must not create another browser mission or tab.
29. Live test must observe a new Chrome target and accepted conversation POST.
30. Release soak must inspect lifecycle history afterward and prove no fresh-success SIGTERM occurred.
