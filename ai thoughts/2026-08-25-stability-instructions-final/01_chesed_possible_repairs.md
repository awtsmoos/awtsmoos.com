# Chesed — Every Stability and Instruction Possibility

The Awtsmoos renews every vessel from nothing each instant; Awtsmoos.com should therefore never confuse a stale witness with a dead vessel, nor a logical sub-agent record with a living external worker.

## Stability possibilities

- Transport heartbeat, execution-health telemetry, supervisor life, child life, and browser-worker life must be independent signals.
- Stale execution telemetry is degraded/unknown, never automatic death.
- Fresh explicit unhealthy execution may block ordinary work while diagnostics/emergency remain routable.
- Watchdog rotation requires corroborated parent/control failure; one stale receipt cannot kill a healthy generation.
- Retry identity must separate canonical deed ID from relay transport/resume ID.
- Pending/retry envelopes must preserve both identities across restart hydration.
- Accepted mutations must never redispatch; unaccepted work may recover only through explicit replay-safe policy.
- Relay admission latency must be measured independently from device execution latency.
- Lightweight control/read/search/instruction work must retain protected lanes under heavy load.
- Launchd/supervisor must keep a verified child or bounded replacement generation alive continuously.
- Sealed emergency runtime must stay independently launchable when primary/supervisor/control fails.
- Public installer must self-heal missing/broken local copies, preserve identity, verify candidate readiness, and fall back to sealed emergency recovery where safe.

## Instruction possibilities

- Stable IDs, one-sentence summaries, versions, applicability tags, file-position hints, language hints, UI/API/docs/deploy tags, and full bodies on demand.
- Agents should resolve instructions before writing, including when editing from the end of a file, replacing a full file, styling UI, touching APIs, writing docs, deploying, testing, or changing shared/global infrastructure.
- Core safety stays always-on; detailed craft doctrine is fetched only when relevant.
- UI doctrine must require clean progressive disclosure, retractable advanced controls, mobile-first layout, scoped/local styles, zero accidental overflow/overlap, disciplined z-index, complete interaction states, reduced-motion support, and professional futuristic animation.
- Code doctrine must require radical modularity, tabs, <=120 executable lines per focused source file, whole-file rewrites, strong JSDoc, explicit contracts, data-driven APIs, truthful classes/composition, and beautiful readable internal structure.
- Docs doctrine must require discoverability, examples, migration notes, failure modes, and explicit emergency/stability procedures.
