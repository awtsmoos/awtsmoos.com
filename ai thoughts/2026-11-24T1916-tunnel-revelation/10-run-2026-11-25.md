# B"H — Tunnel Revelation Run 10: chooser regression + Copy contrast — 2026-11-25

Scope: `geelooy/apps/tunnel` ONLY. Fixes the 2 defects from the beauty
re-verification (live browser, returning session): the method chooser was
dead again (it had PASSED the run-04 browser re-check), and the Copy
button in the dark Install panel was near-invisible.

## Defect A — chooser dead in a returning browser

### Evidence gathered from production, in order
- Served `index.html` pins verified: `onboarding.js?v=d77f6b4a0a`,
  `main.js?v=03e89a2b0d`, `tunnel.css` — every pin equals the first 10 of
  the served file's SHA-256. `onboarding.js` serves 200,
  `Content-Type: application/javascript`, mode 644 (the run-04 403 is
  gone), body byte-identical to disk.
- Fresh-profile CDP (server Chrome 157): chooser mounts, detail filled,
  Browser/Virtual clicks switch pressed state, detail and Continue label.
  Warm second load (HTTP cache): same PASS. No console exceptions, no
  failed requests.
- Returning-browser scenario reproduced properly — homepage first so the
  service worker (awtsmoos-v6, scope `/`) registers and CONTROLS the
  tunnel page, then two tunnel loads: chooser PASS both times, clicks
  PASS. The current SW's script handling (network, `no-store`) does not
  break the module.
- So no current-code defect reproduces in a clean or SW-controlled
  profile. What the failing session showed is exactly the zero-JS markup
  state: `#onboardDetail` shipped EMPTY, Native is `aria-pressed="true"`
  in the raw HTML, Continue shipped as a bare "Continue" — i.e. in that
  session `onboarding.js` never executed at all, while HTML/CSS rendered.
  That session's other evidence points the same way: its status and
  missions fetches also never answered (server load was 17–26 during
  those checks; a single failed module fetch through the SW's no-store
  fetch, which has no fallback, is enough).

### Root cause
The chooser depended on ONE module fetch, and the page shipped an empty
shell that only that module could fill. Any single failure of that fetch
— gateway error under load, a poisoned/stale cache entry in a returning
browser — left a permanently dead chooser with no retry and no fallback.
Fresh CDP profiles never see it; returning browsers under load can.

### Fix (at the root, in `index.html`)
1. The markup now SHIPS the native default state: `#onboardDetail`
   contains the native detail text and `#onboardGo` reads
   "Continue: Native tunnel on your own computer". Zero-JS renders a
   complete, honest chooser.
2. An inline resilience guard (classic script, part of the HTML —
   `Cache-Control: no-cache, must-revalidate`, so every returning
   browser gets it fresh even if its JS caches are poisoned): 2.5s after
   `load`, if `data-onboarding-mounted` is unset, it re-imports the
   pinned module URL with a cache-busting `&r=` retry; if that import
   also fails, it binds a minimal inline chooser (same three methods)
   so the buttons always work.

### Proof
- Deterministic mirror proof (local mirror of the app, real Chrome):
  - Scenario A — first two `onboarding.js` requests return 500, the
    third succeeds: the guard's retry import mounted the REAL module
    (`mounted="1"`, 3 hits total), Virtual click switched correctly.
    PASS.
  - Scenario B — `onboarding.js` always 500: guard bound the fallback
    (`mounted="fallback"`), Virtual click switched correctly. PASS.
- Production CDP after the fix: warm load 1 and warm load 2 (same
  profile, SW + HTTP cache warm) — chooser mounts, Browser and Virtual
  clicks switch pressed state, detail and Continue label. PASS.
- New regression test `test/chooserResilience.test.cjs` asserts the
  shipped default text/label and the guard's presence. PASS.
- Widths after fix (CDP): 320 / 390 / 1280 — layout width == scroll
  width at 320 and 390 (1280: scroll 1265 < inner), 7 steps present,
  detail filled at every width.

## Defect B — Copy button invisible on the dark install panel

### Root cause (computed-style evidence, light scheme)
The beauty layer (run 09) made `.command-card` deep espresso
(`#1d1201 → #120b01`) in BOTH schemes. But `.button.small` takes its
text color from `--aw-text`, which the tokens sheet sets to `#2a1d05`
(near-black) in the light scheme, and the button's own background is a
translucent gold wash — over the espresso card it composites to dark
brown. Measured pre-fix in real Chrome (light): Copy computed
`color: rgb(42, 29, 5)` sitting on the espresso card. Dark text on a
dark surface. Every other button on the page sits on a light panel in
the light scheme (Start/Stop/Refresh measured 15.57:1) — the command
card was the only dark surface holding buttons. (In the dark scheme
`--aw-text` is near-white, so the trap only armed in light.)

### Fix (`css/tunnel.css`, appended Run-10 layer, after the light block)
`.command-card .button` now always wears champagne text `#ffedb3` on a
visible gold-glass gradient with a `rgba(255,197,66,0.62)` border, in
both schemes; `:disabled` on dark surfaces keeps `#e8cf8f` at 0.75
opacity — muted but legible.

### Proof (real Chrome, light scheme, gradient-aware compositing)
- Copy: color `rgb(255, 237, 179)`, effective background
  `rgb(112, 89, 28)`, **contrast 5.72:1** (≥ 4.5). Screenshot read
  personally (`/root/run10-shots/install-panel-light.png`): "Copy" is
  bright champagne on a bordered gold-glass button inside the espresso
  card — unmistakably legible. Start/Stop/Refresh re-measured 15.57:1,
  Stop (disabled) legible.
- Dark scheme width runs confirm the same `rgb(255, 237, 179)` Copy
  color at 320/390/1280.
