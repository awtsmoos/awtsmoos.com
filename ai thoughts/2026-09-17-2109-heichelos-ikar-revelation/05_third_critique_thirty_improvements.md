# Boruch Hashem — Third Critique: Thirty Further Improvements

Blessed is He.

A plan can call itself complete while a hidden edge remains;
the Awtsmoos renews the witness and dissolves imagined chains.
Awtsmoos.com must earn its clarity in source, in touch, in route, in test;
one Ikar Torah library, with every surrounding vessel doing what it does best.

## Thirty additional refinements

1. Read route definitions before interpreting URL conventions from filenames.
2. Read the generic index template and its direct partial dependencies completely.
3. Read the existing Ikar-first tests before changing their intended contract.
4. Identify the actual Ikar alias/id from source or live DOM rather than hard-coding a guess.
5. Inspect whether cards are server-rendered or client-rendered before choosing a view boundary.
6. Inspect data shape for Heichel type/category metadata before inventing new flags.
7. If no formal Torah/category metadata exists, use the proven canonical Ikar identity narrowly rather than classifying every space heuristically.
8. Preserve discoverability for Bais Shimon and other community spaces in a clearly secondary community section.
9. Do not move moderation/submission controls into the Torah reader surface.
10. Ensure the featured Ikar card has one dominant CTA and understandable supporting text.
11. Ensure card order does not depend on unstable network timing.
12. Ensure failures to load community spaces do not make Ikar inaccessible.
13. Ensure failures to load Ikar metadata produce a stable canonical fallback link only if its route is verified.
14. Inspect global navigation offsets before adding sticky UI.
15. Inspect existing CSS tokens/custom properties before introducing duplicate colors/spacing systems.
16. Reuse existing visual primitives when they are coherent; replace only proven broken composition.
17. Check 320–360px layouts, not merely a generous desktop emulation.
18. Check text zoom/long titles so cards do not overflow.
19. Preserve RTL/Hebrew-capable layout semantics if present in surrounding code.
20. Avoid relying on hover for any essential action.
21. Ensure focus rings remain visible after restyling.
22. Ensure `aria`/semantic labeling of tabs or filters survives any navigation rewrite.
23. Inspect history/popstate behavior if tabs alter URLs.
24. Make search error rendering robust even if optional error-panel elements are missing.
25. Avoid swallowing search failures silently; present useful state while logging enough context.
26. Differentiate empty search results from failed search requests.
27. If the `dataset` crash stems from event target assumptions, normalize/validate targets before reading data attributes.
28. If it stems from missing queried elements, centralize the acquisition contract rather than duplicating guards.
29. Add a regression test reproducing the exact absent-node or invalid-target shape found in the stack.
30. Check console after initial load and after interaction, not only page load.
31. Inspect network/API failures during browser reproduction so rendering errors are not misdiagnosed as data errors.
32. Confirm live asset caching does not mask rewritten source; hard reload or cache-bust where tooling permits.
33. Run current tests before edits if practical after inspection, establishing which failures pre-exist.
34. Never “fix” unrelated pre-existing failures without evidence they intersect this work; record them separately.
35. After code, compare touched-file count against the final architecture and remove unnecessary churn.
36. Read all rewritten files from disk, not from the intended write payload.
37. Verify every rewritten source file starts with the required B"H/Boruch Hashem/Blessed is He prologue where syntax permits.
38. Verify tabs for indentation and eliminate mixed indentation in touched source.
39. Verify no touched function is compressed into one line.
40. Verify no duplicate implementation remains after any module split.
41. Confirm imports resolve from browser/server perspective, including relative-path casing.
42. Run focused tests first, then the broader relevant test set.
43. Capture final mobile screenshot or DOM snapshot as behavioral evidence.
44. Verify the user-visible phrase “Torah Library” appears only where it leads into Ikar within the redesigned scope.
45. Verify generic community Heichelos do not inherit Torah-specific labels by accident.
46. Verify direct community deep links still work after gateway changes.
47. Verify Ikar post and series deep links still work after shell changes.
48. Record planned-versus-actual delta after the first implementation pass.
49. Perform a correction pass for every meaningful delta before final reporting.
50. End only when the remaining-work ledger contains no safe in-scope executable item.

## Final critique conclusion

The strongest path is not a redirect and not a new parallel app. It is a restrained consolidation: make Ikar the explicit canonical Torah library, reshape the generic Heichelos surface around purpose, repair search at its actual failing boundary, and prove the result through tests plus a mobile browser run.
