# Verification and release contract

B"H

## Verification ladder

Use the deepest relevant layer available:

1. Source readback.
2. Static or syntax validation.
3. Focused unit or module checks.
4. Integration/API verification.
5. Runtime or browser interaction.
6. Deployment activation evidence.
7. Live public response.
8. User-visible behavior on the affected surface.

A higher layer does not excuse skipping the lower layer needed to catch accidental source corruption.

## Evidence discipline

- Attach each completion claim to observed evidence.
- Preserve request IDs, hashes, revisions, or release IDs when useful and safe.
- After timeout, reconcile status before replaying a write or deployment.
- Distinguish correlation IDs from durable idempotency guarantees.
- Verify final bytes or behavior after rollback, retry, or concurrent changes.

## Deployment

- A push is not deployment.
- A build is not activation.
- Activation is not proof of live user-visible behavior.
- Fetch or inspect the actual target after deployment when reachable.
- Use unique markers, hashes, or revisions to distinguish new bytes from CDN or cache leftovers.

## Plugin publication

- Preserve existing identity, prompts, assets, integrations, and metadata unless the user asked to change them.
- Bump version deliberately.
- Read the published source back after update.
- A skill can teach an authentication process but cannot create a callable action merely by describing one.
- Test a fresh invocation when possible because an existing conversation can retain an older instruction snapshot.

## Final improvement pass

Review touched work for correctness, maintainability, performance, security, accessibility, error handling, and obvious UX defects as applicable. Fix material findings and re-verify them. Stop when a bounded pass finds no material relevant issue.
