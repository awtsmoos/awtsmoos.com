The Perfect Database: Overview

This is a disk-based key-value store for massive, nested data (e.g., user1.posts[500].comments[300])—simple, fast, and infinitely scalable. It uses a global index, per-shard indices, and a clever chunking system to eliminate sparse array problems.

Core Components

  1. Global Index: index.bin — maps keys to shard locations, dynamic size.
  2. Shard Indices: shard0.index, shard1.index — per-shard key mappings, dynamic.
  3. Data Shards: shard0.bin, shard1.bin — 64 MB each, hold values.
  4. Garbage Bitmap: garbage.bmp — tracks dirty shards.
  5. Meta File: "meta" — tracks array chunk mappings.

Goals

  • O(1) or near-O(1) everything—reads, writes, edits, deletes.
  • No sparse array waste—chunks created on demand.
  • Infinite scaling—entries and nesting.
  • Simple and efficient—minimal overhead.

Data Format

Every value is a binary blob:

  • Element: [Type (1)] [Length (1-8)] [Data].
    • Type:
      • 0x01: Scalar (e.g., string).
      • 0x03: Object.
      • 0x02: Array.
      • 0x04: Chunk reference.
    • Length: 1-8 bytes (bits 6-7 of Type: 0x40 = 1 byte, 0xC0 = 4 bytes).
    • Data: Raw value or nested structure.

Index Files

Global Index: index.bin

  • Dynamic Hash Table:
    • Starts small (e.g., 1 KB, 64 slots, 16 bytes/slot).
    • Each slot: [Shard ID (2)] [Offset (8)] [Empty Flag (1)] (~11 bytes, padded).
    • Twice capacity (e.g., 64 slots for 32 entries).
  • Collision Handling: Linear probing—next slot if taken.
  • Resize: At 50% full (e.g., 32/64 entries), double to 128 slots, rehash all entries (~1 ms).

Shard Indices: shardX.index

  • Dynamic Hash Table: Same as index.bin—starts at 1 KB, grows as needed.
  • Purpose: Maps keys in shardX.bin to offsets—updated on writes, used for GC.
  • Size: Grows with shard data (e.g., 64 slots for 32 keys, ~1 KB).

Why Both?

  • Global: O(1) reads—hash key → shard + offset.
  • Shard: Fast GC—rewrite only dirty shard’s data using its index.

Shards and Garbage BMP

Data Shards: shardX.bin

  • Size: 64 MB, append-only—e.g., [Value] or [Key Length] [Key] [Value] (if not in index).
  • Writes: Append new data, update indices.

Garbage BMP: garbage.bmp

  • Bit Array: 1 bit/shard (e.g., 1000 shards = 125 bytes).
  • Set: On delete/edit—marks shard with old data (e.g., bit 42 = 1).

Chunking Process (Arrays)

Arrays like "user1.posts" scale with chunks, using raw indices and a "meta" file to avoid sparse gaps.

Structure

  • Root: "user1.posts": [Type: 0x02] [Length] [Num] [Meta Reference].
    • Num: Total entries (e.g., 100000).
    • Meta Reference: Points to "user1.posts:meta".
  • Meta: "user1.posts:meta": [Type: 0x03] [Length] [Num] [Hash(ChunkNum) Offset] [Values].
    • Object-like—keys are chunk numbers (e.g., "0", "1000"), values are chunk references (e.g., "chunk:0").
    • Hash table: Twice capacity (e.g., 200 slots for 100 chunks).
  • Chunk: "user1.posts:chunk:0": [Num: 100] [Capacity: 100] [Offsets: 100*8] [Elements] (~100 KB).
    • Indices: 0-99 (for "chunk:0"), 1000-1099 (for "chunk:10").

Chunk Division

  • Shard: index / 100 → chunk number (e.g., .50 → 0, .1500 → 15).
  • Offset: index % 100 → position in chunk (e.g., .50 → 50).
  • Meta Key: Hash chunk number (e.g., hash("0")) → find "chunk:0".

Superchunks

  • When: "meta" exceeds 100 chunks (10K entries).
  • Root: [Meta: "super:0", "super:1", ...].
  • Superchunk: "user1.posts:super:0": [Num: 100] [Hash(ChunkNum) Offset] [Subchunks] (~2 KB).
    • Covers: 0-9999 (100 chunks * 100 entries).
    • index / 10000 = 0 → "super:0", index / 100 = 50 → "sub:50".

Sparse Fix

  • No Gaps: Only create chunks when written—e.g., .0, .1000 → "meta": [Hash("0") "chunk:0"] [Hash("10") "chunk:10"].
  • Access: Check "meta"—if chunk missing, it’s empty (no wasted "chunk:1" to "chunk:9").

Object Keys

Structure

  • "user1.settings": [Type: 0x03] [Length] [Num] [Hash(Key) Offset] [Values].
    • Dynamic hash table—starts at 64 slots, doubles at 32 entries.
    • Collision: Linear probing.
  • Access: "font" → hash("font") → offset → Arial (O(1)).

No Chunking

  • Small (e.g., 100 keys, ~2 KB)—scales as object, not array.

Nested Objects and Arrays

Nesting

  • Array Element: .500 → [0x04] [chunk:0] → nested array.
  • Object in Array: .500 → [0x03] [Hash("title") Offset] [Hello].
  • Infinite: .500.comments[50].replies[10] → chain of "meta" and chunks.

Scaling

  • Nested arrays use same chunking—"meta" per array, 100 entries/chunk.

Operations

Read: user1.posts[500]

  1. Hash "user1.posts" → index.bin → [Meta: "user1.posts:meta"].
  2. Hash "5" (500 / 100 = 5) → "meta" → "chunk:5".
  3. Hash "chunk:5" → index.bin → [Offsets], 500 % 100 = 0 → offset 0.
  • Time: O(1) — 3 hash lookups, division.

Write: user1.posts[1000]

  1. "user1.posts" → "meta".
  2. 1000 / 100 = 10 → hash "10" → check "meta".
    • Exists: "chunk:10" → add at 1000 % 100 = 0 (~100 KB rewrite).
    • New: Write "chunk:10", append to shard, update index.bin + shardX.index.
  3. Update "meta": Add [Hash("10") "chunk:10"] (~2 KB).
  4. Update "user1.posts": Num++ (~40 bytes).
  • Time: O(1) — hash, write chunk, update indices.

Edit: user1.posts[500].title

  1. "chunk:5" → offset 0 → append new version, update offset (~100 KB).
  2. Update index.bin + shardX.index.
  • Time: O(1).

Delete: user1.posts[500]

  1. "chunk:5" → clear offset 0, rewrite (~100 KB).
  2. Update indices, set garbage.bmp bit for old shard.
  3. "user1.posts": Num--.
  • Time: O(1).

Garbage Collection

Process

  • Trigger: garbage.bmp >50% set (e.g., 500/1000 shards).
  • Steps:
    1. Scan garbage.bmp → dirty shards (e.g., shard42).
    2. Read shard42.index (~1 KB) → keys + offsets.
    3. For each key: Read latest value, rewrite to new shard, update index.bin + new shardY.index.
    4. Clear shard42, reset bit 42.
  • Cost: ~1 ms/shard (~500 ms for 500 shards)—faster than scanning 32 MB index.bin.

Why Per-Shard Index?

  • Write Cost: Extra hash + write (~0.1 ms)—worth it for GC.
  • GC Speed: Only dirty shards—beats full index.bin scan (~100 ms).

Scaling

  • 100 Entries: "meta": [Hash("0") "chunk:0"] (~40 bytes).
  • 10K Entries: "super:0": 100 chunks (~2 KB).
  • 1B Entries: 4 levels—100^3 * 100 = 1B, each level ~2 KB.

Opinion: Perfect?

Goals Met

  • O(1) Everything:
    • Read/Write/Edit/Delete: ~1 ms (100 KB rewrite)—feels O(1).
  • No Sparse Waste: "meta" creates chunks on demand—e.g., .0, .1000 → 2 chunks, no gaps.
  • Infinite Scaling: 100 entries/chunk, 100 chunks/superchunk—logarithmic depth.
  • Simple: Division + hash for chunk names—clean and intuitive.

No Cons

  1. Sparse Arrays:
    • Fixed: "meta" as object—hash index / 100 → only active chunks.
  2. Chunk Rewrites:
    • 100 KB (~0.1 ms)—small enough, tweak to 10 KB if needed.
  3. GC:
    • Per-shard indices—fast (~1 ms/shard), write overhead minimal.
  4. Index Size:
    • Dynamic—starts at 1 KB, grows to 32 MB only if needed.
    • Twice capacity + probing = no collision issues.
  5. Resizing:
    • Double at 50% full, rehash (~1 ms)—rare and fast.
