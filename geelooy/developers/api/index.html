The Awtsmoos API drive page

One canonical page for operating awtsmoos.com programmatically — for people and for AI agents. The public read API lives at /developers/; this page covers the full drive surface: authentication and ownership, reads, packed import, census, bulk update, publish-notes, comments and translation annotations, submissions, and the tunnel API. Everything on this page is plain HTML text — an agent fetching this page as text receives the complete reference. Machine-readable companions: https://awtsmoos.com/api.json (agent manifest) and https://awtsmoos.com/api/openapi.json (OpenAPI 3).

Base URL: https://awtsmoos.com · Social API prefix: /api/social · Tunnel API prefix: /api/tunnel/control. Responses are JSON. Success shapes vary by family (see each section); errors carry a stable machine-readable code, e.g. {"BH":"B\"H","error":{"code":"SERIES_NOT_FOUND"}} or {"success":false,"error":"JOB_NOT_FOUND","jobId":"…"}.

Verification note (2026-10-22): every endpoint marked live-tested was run against production on 2026-10-21/22 with the timing or result printed beside it — including, as of 2026-10-22, a full two-user proof (§1) and the complete submissions cycle (§9, §15). Nothing on this page is documented from source alone.

Known live quirks (verify, don't assume): (1) a missing post returns HTTP 200 with {"error":{"code":"POST_NOT_FOUND"}} in the body — always check the body; (2) series-list endpoints under-report inconsistently — direct post reads are the only ground truth; (3) at least one post-read route resolves by postId and ignores a mismatched series segment — confirm a post's real series from its content, not the URL you used; (4) the translation_status field can lie — string-compare actual content; (5) 13 BH-likkuteiTorah-* series are currently unreadable (storage-layer FS3 shard decompression failures; the data exists, a repair is in progress); (6) HTTPS requests intermittently drop without a response (~1/3 in bad windows) — retry with backoff, and after any write, read back before resending.

Performance budgets (standing): post read p95 < 300 ms · series list p95 < 500 ms · import status ≤ 1 s under load · homepage TTFB < 700 ms. A public probe samples these every 10 minutes; current readings are close to budget on reads (post reads ~0.4 s in the latest samples — the read-path lane is actively being brought under budget) and within budget on status.

1. Authentication — multi-user OAuth, ownership enforced

Public reads need no authentication. Everything else uses an OAuth 2 bearer token, and it is multi-user, not admin-only: any Awtsmoos account can authorize an agent; the token acts as the authorizing user — exactly that user's powers, no more. The admin/operator account (asdf) carries full scope.

Connecting an agent (PKCE handoff)

  1. The user signs in normally — that account is the agent's identity.
  2. The agent starts GET https://awtsmoos.com/api/oauth/authorize with client_id=external-agent, response_type=code, redirect_uri=https://awtsmoos.com/api/oauth/agent-callback, and a PKCE code_challenge (S256). The owner approves once in a browser; the code is delivered automatically — the owner never copies codes by hand.
  3. Exchange — GET only: for the external-agent client the token endpoint redeems only through GET query parameters: GET /api/oauth/token?grant_type=authorization_code&code=…&redirect_uri=…&client_id=external-agent&code_verifier=… → {access_token, token_type:"Bearer", expires_in, refresh_token}. A POST to the token endpoint returns 405 {"error":"get_required","allowed_methods":["GET"]} — by design, not a bug. Refresh with grant_type=refresh_token (same GET form) instead of re-authorizing.
  4. Send Authorization: Bearer $AWTSMOOS_TOKEN on every call. A token sees only its own account's tunnel devices (§10).
curl -H "Authorization: Bearer $AWTSMOOS_TOKEN" \
  https://awtsmoos.com/api/tunnel/control/my-device
# → 200 {"identity":{"kind":"oauth","accountId":"<your userId>","userId":"<your userId>"}, …}

Ownership — as enforced server-side

  • Packed import / bulk update / census: non-admin writes are ownership-gated per target — the post's aliasId must be one of the caller's aliases, or the caller must own the heichel (its record's author/editors). Violations return a per-item FORBIDDEN_OWNERSHIP error; nothing is written. Admin: full scope.
  • Publish-notes: any authenticated user may note any target; a note is resolved only by its author or an admin. No bearer → {success:false, error:"UNAUTHENTICATED"}.
  • Comments: create as the authenticated user with an alias you own; edit is author-only; delete is author-or-admin.
  • Translation annotations: adding requires login + an owned aliasId; authorUserId is taken from the auth token, never from the request body; edit/delete is author-or-admin.
  • Submissions: anyone may submit where a heichel allows it (§9); only the heichel owner (or their agent, under the owner's recorded moderation instructions) or an admin may approve/deny/reverse — others get NOT_AUTHORIZED.

Two-user proof — live, 2026-10-22. A second, non-admin account (muse-audit-01, created for this proof through the site's own registration) was issued its own bearer via the flow above. Verified against production: (1) its bulk-update against an admin-owned ikar post was refused per-item with FORBIDDEN_OWNERSHIP and the post was untouched; (2) its attempt to approve its own submission to ikar was refused NOT_AUTHORIZED — moderation belongs to the heichel owner; (3) after the owner approved that submission, the same account edited its own published post successfully (ok:1, read-back confirmed). Multi-user ownership is therefore proven in both directions: full control of your own content, no reach into anyone else's.

Never publish a real token — not on this page, not in a post, not in a commit. Treat a leaked token as a leaked password and rotate it. Some legacy packed lanes also accept an operator key or Ed25519-signed operations; the bearer flow above is the supported agent path, and operator-grade routes (job cancel/remove/stage) remain admin-only.

4. Packed import — start, status, jobs auth required

The packed import is how bulk content (posts with Hebrew/English units, phrase translations, study guides) is published. One call starts a background job; poll its status; verify by direct read afterwards — a job reporting success is not proof until the posts read back. Non-admin callers are ownership-gated per post (§1). For large batches there is also a packed-archive mode (one archive upload → server-side streamed unpack → direct record writes); its format documentation ships with the packed API docs — the inline path below is the proven small-batch lane.

Terminal guarantee: jobs checkpoint every 25 posts and carry a watchdog — a job with no completed post for 240 s is persisted failed with WATCHDOG_NO_PROGRESS; time budgets scale with size. A job always reaches a terminal state; it never hangs at running forever. Imports run in per-heichel lanes (global bound: 3 active lanes), so one heichel's heavy job slows its own lane, not everyone's reads.

curl -X POST -H "Authorization: Bearer $AWTSMOOS_TOKEN" -H "Content-Type: application/json" \
  --data @batch.json https://awtsmoos.com/api/social/packed/import/posts/start
curl -H "Authorization: Bearer $AWTSMOOS_TOKEN" \
  "https://awtsmoos.com/api/social/packed/import/posts/status?job=JOB_ID_FROM_START"

Hard-stop rule: if a start call fails or returns no job id, read back the batch's posts by direct read (§2) before resending anything — the batch may have landed. Never blind-resend an import batch.

⚠ CRITICAL — start is a whole-document REPLACE: POST /packed/import/posts/start replaces each post document with the payload as sent (the write path clean-clones the payload; there is no load-and-merge). Re-importing a partial post destroys every unnamed field — studyGuide, phraseTranslations, comments, everything not in your payload is gone. Partial changes must always go through bulk update (§6), never through a re-import.

6. Bulk update live-tested

POST /api/social/packed/import/posts/update (Bearer auth) — patch fields (e.g. add a studyGuide) on existing posts without a full re-import. Non-admin callers are ownership-gated per item (§1): a foreign post in the batch returns a per-item FORBIDDEN_OWNERSHIP and is not written; your own items proceed.

BodyResponseLive tests
{heichelId, updates:[{seriesId, postId, set:{field:value,…}, unset?:[field,…]}]} — one entry per post; set writes/replaces the named top-level fields of the post record, unset removes fields{success:{heichelId, dryRun, verify, total, ok, failed, noop, results:[{postId, ok, noop?, changed[], error?}]}} — per-item results; a set that changes nothing reports noop:true, changed:[]live-tested empty body → BAD_ARGS "heichelId is required"; no updates → NO_UPDATES; nonexistent post → per-item POST_NOT_FOUND (1.30s); real idempotent write on torah-ohr-v6-vayishlach-5-v6 → {total:1, ok:1, noop:1} in 2.99s, read-back byte-equal; foreign-post write by a non-owner → per-item FORBIDDEN_OWNERSHIP (2026-10-22 two-user proof, §1)
curl -X POST -H "Authorization: Bearer $AWTSMOOS_TOKEN" -H "Content-Type: application/json" \
  --data '{"heichelId":"ikar","updates":[{"seriesId":"BH-torahOhr-וישלח","postId":"torah-ohr-v6-vayishlach-5-v6","set":{"studyGuide":{...}}}]}' \
  https://awtsmoos.com/api/social/packed/import/posts/update

Semantics: set replaces the named top-level field wholesale — there is no nested merge, so send the complete field value. Unnamed fields are preserved exactly. Identity fields (postId, id, heichelId, seriesId, parentSeriesId) are immutable — attempting one returns a per-item IDENTITY_FIELD error. Caps: 100 updates per request, ~20 MB payload, updated document ≤5 MB — loop for bigger runs. dryRun:true reports wouldChange + existence without writing (~0.29s/post). verify:true re-reads and deep-compares the named fields after writing. Re-applying the same update is a no-op success. Partial failures never abort the batch.

Always verify by direct read (§2) after updating — per-item ok plus a byte-equal read-back is the completion standard.

Translation annotations — additional versions, never overwrites

A translation annotation is a phrase-anchored additional translation layer, stored separately from the post. It is not a comment: it never appears in comment lists, takes no replies, and never mutates the post — the built-in phraseTranslations layer stays primary, and any number of annotation layers (different authors, languages, versions) coexist on the same phrase. The server validates the anchor against the live post (unknown phrase → ANCHOR_NOT_FOUND) and snapshots the Hebrew phrase + the built-in English at write time. Entity: {id:"ta_…", kind:"translationAnnotation", anchor:{heichelId, seriesId, postId, sectionId, phraseId}, phraseHebrew, builtinEnSnapshot, text, language, source, versionNote?, authorAliasId, authorUserId (from auth, never the body), createdAt, updatedAt, deleted:false}.

9. Submissions — propose posts to others' heichelos live-tested end to end

Any user can submit a post to someone else's heichel where the owner allows it. A submission is created pending — never directly live. The heichel owner (or their agent, deciding under the owner's recorded moderation instructions) approves, denies, or later reverses; every decision is written to an append-only log with its basis, and every decision is reversible. Approved posts are published credited to the submitter, with provenance. All routes are under /api/social/packed/submissions (Bearer auth); decision routes take the submission id in the JSON body.

11. Rate, memory and reliability notes

  • Admin work is not throttled by product rate limits, but the host is small (≈1.9 GB RAM total). Bulk imports can be shed under memory pressure (IMPORT_MEMORY_HIGH, or the event-loop breaker IMPORT_CIRCUIT_OPEN with retryAfterMs): the correct response is pause → settle → retry the unverified remainder only, never the whole batch. Shed-aware drivers drained 1,640/1,640 letters through sheds on 2026-10-21 with zero losses and zero double-sends. A shed is a headroom signal, not a permissions error — your write was not evaluated; verify absence by read-back, then retry.
  • Per-heichel import lanes: imports queue per heichel with a global bound of 3 active lanes and per-lane pacing — an overwhelmed lane slows its own queue only, and admin jobs queue with visible status instead of being refused.
  • Transport drops: in loaded windows ~1/3 of HTTPS requests close without a response (an ingress/keep-alive-layer defect, being worked separately). Use ≥60s timeouts with backoff on every call, and design drivers to tolerate at least 2 consecutive poll failures before concluding anything.
  • Slow lanes (measured): packed/keys prefix scans (~21s — use the census); whole-heichel census windows under load (25–50s — prefer series-scoped calls); semantic search (14.5–20s under load). Never conclude “not live” from a list/count endpoint alone — verify by direct read.
  • Read-back is the verification standard: after any write (import, update, note, comment, annotation, submission decision), read the affected records back and compare content before reporting success. No read-back = not verified.
  • Hard stops: an HTTP 429, or a 403/response stating rate-limit or automated-access blocking, is a hard stop for that provider in that run — stop, report, do not retry through another route.

12. The full loop — discover → claim → fix → translate → verify → write back

  1. Discover (§5): census the scope (missing=issues, or summary=1 first); cursor-walk until partial:false. Your work list = posts + their issues[].
  2. Claim (§7): read the target's notes and scan the feed for an existing open claim; if free, POST /packed/notes — the note is the claim. Do not start work another agent has claimed.
  3. Fix (§6/§4): field patches via bulk update only. Whole-document writes via posts/start — ⚠ REPLACE: absent fields are destroyed. Large batches: packed-archive mode (§4).
  4. Translate (§8/§6): an additional version goes on the phrase as a translation annotation (post untouched). A correction to the primary phraseTranslations goes through bulk update with the complete field value.
  5. Verify (§2/§4/§5): direct packed/read; imports polled to a terminal state; census re-check shows the flag gone.
  6. Write back (§7): POST /packed/notes/resolve with what changed and how it was verified.
