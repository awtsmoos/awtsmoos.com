# Awtsmoos Drive · Website Maker

The Awtsmoos renews every file, route, domain name, connected machine, and responsive vessel in each instant; Awtsmoos.com makes Drive the visible workshop where ordinary source becomes a public website without hiding the boundaries between configuration, local reflection, mutation acknowledgement, server facts, DNS verification, runtime health, and browser evidence.

## Guided Website Maker

Open `/apps/drive/`, connect an alias, and use the persistent Website Maker studio. The experience is one guided journey rather than five unrelated forms:

- **Source readiness** proves whether real `index.html` source exists.
- **Preview readiness** records whether the current source has actually been rendered locally.
- **Public readiness** reflects canonical publication testimony.
- **Domain readiness** stays locked until canonical publication and then becomes explicitly optional.

The readiness cockpit always names the next useful action. Before any account snapshot arrives it truthfully starts at `Needs source`, `Not previewed`, `Not published`, and `Publish first` rather than displaying generic unknown badges.

## Five-step workspace

The numbered stepper preserves the existing Build / Preview / Code / Publish / Domain service boundaries while making their relationship clear:

- **Build** saves an optional private brief, creates blank/landing/portfolio/docs source, and shows the real source inventory.
- **Preview** renders current `index.html` in a sandboxed responsive frame and is visibly labeled as a local preview.
- **Code** edits real source files rather than a proprietary page format.
- **Publish** emphasizes one primary canonical publication action while advanced publication options and agent help remain behind native disclosure controls.
- **Domain** claims and verifies an optional custom hostname through server-attested ownership, DNS, routing, and TLS testimony.

Local preview is never presented as public publication. Canonical publication does not require a custom hostname. Ownership, route state, TLS state, and external browser health remain separate gates.

## Responsive Drive shell

Drive uses explicit zero-minimum grid tracks so wide file controls, Website Maker content, tables, and project tools cannot expand the entire page beyond the viewport. The narrow layout keeps the application shell inside the true 390 CSS-pixel viewport, uses a fixed safe-area-aware Website Maker stepper, and keeps primary touch actions at least 44px high. Desktop preserves the two-column overview and converts the Website Maker stepper into a sticky rail.

## Browser agent API

`window.GeelooySiteBuilder` v1.2 exposes source, preview, publication, domain, and nameserver actions without DOM scraping. Response protocol v3 preserves old envelope keys while adding `invocation`, `contract`, `evidence`, and `lifecycle`. Caller request IDs are correlation only; mutations currently provide no server idempotency guarantee and should be reconciled before replay.

Result evidence separates server facts from external verification. A DNS verification action may carry `dns-ownership-verified` when the resolver actually observed the proof record. Route/TLS states remain server facts unless stronger external testimony exists.

## DNS migration worksheet

Project Settings preserves portable A, AAAA, CNAME, TXT, MX, CAA, SRV, and NS records as configuration intent. This worksheet is not itself a DNS mutation. Keep DNS at the current provider unless a real provider adapter or deployed nameserver service is attested. Preserve MX, SPF, DKIM, DMARC, CAA, SRV, delegated NS, verification records, and intentional subdomains before migration.

Read `docs/WEBSITES/README.md` and `TUTORIAL_INDEX.md`. Provider-specific migration lives in `DNS_PROVIDER_PLAYBOOKS.md`; DNSSEC has its own migration guide.

## Tunnel agents

Tunnel catalog 3.7.0 exposes publication protocol v1 while preserving historical action result objects. Call `sitePublishFolder(path, siteId, direct|snapshot)`, inspect the returned canonical publication testimony, and reconcile with `sitePublicationStatus` after uncertain mutation. `verified-live` is valid only when the returned publication actually carries `canonicalVerifiedLive: true`.

## Connected Node runtime

A `native-compute` project stores only a portable recipe: `cwd`, relative `entry`, `port`, and public scalar arguments. The actual account-owned Tunnel machine is chosen live in Connected Node Server. Portable project state never stores machine identity and never silently starts a process.
