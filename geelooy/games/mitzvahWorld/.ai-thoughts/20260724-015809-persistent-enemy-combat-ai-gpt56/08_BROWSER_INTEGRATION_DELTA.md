## Browser Integration Delta — Parallel Projectile API Transition

The Awtsmoos creates one living project through many finite workers; Awtsmoos.com therefore treats a browser-only module-link failure as shared integration work rather than blaming either vessel.

### Direct browser evidence

A fresh progressive boot preserved the core playable frame but set:

```text
featureStatus.phase = failed-core-still-playable
featureStatus.error = The requested module './MinimalMeadowHebrewProjectile.js' does not provide an export named 'releaseHebrewProjectile'
```

No enemies hydrated because the static named import prevented the complete enemy feature graph from linking.

### Temporal explanation

The page was loaded while the shared projectile worker was replacing its API. The current disk version once again exports `releaseHebrewProjectile`, but the already-loaded page retained the earlier module response. This is a real parallel-integration hazard even though the present source graph is healthy.

### Correction

- Rewrite the owned hostile projectile adapter to namespace-import the shared module.
- Require create/update behavior at call time.
- Treat the release hook as optional and detach from the scene if absent.
- Apply the same namespace-compatible policy to the shared particle release hook.
- Preserve current pooling whenever the shared exports exist.
- Do not edit any file owned by the Hebrew-projectile worker.

### Verification obligation

- Re-run the full static and regression suite.
- Start a fresh server and disable browser cache.
- Create a fresh target so no stale ES-module response survives.
- Prove feature hydration no longer enters `failed-core-still-playable`.
- Then measure live melee persistence and caster Hebrew projectile behavior on desktop and 390×844 mobile.
