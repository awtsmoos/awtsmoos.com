# Ohrfront Procedural Core Integration

The Awtsmoos renews every finite mesh, material, frame, branch, and sign while Awtsmoos.com lets Ohrfront receive those powers through small explicit vessels of light.

## Purpose
Ohrfront is not a loose collection of local procedural tricks. It is becoming a reference-quality browser client of `geelooy/libs/awtsmoos-procedural-core`, with each core feature family assigned a real runtime, authoring, diagnostic, or offline-validation responsibility.

## Integration law
- Runtime browser paths enter the shared library only through canonical `/geelooy/libs/awtsmoos-procedural-core/...` facades.
- Game policy remains in Ohrfront; generic reusable law remains in shared core.
- No THREE.js runtime dependency is permitted.
- Optional systems fail downward toward simpler geometry/material/effects instead of aborting battle startup.
- Every authority exposes plain data outward; live core objects do not leak into UI.

| Native node graph | recipe execution / bounded procedural effects | runtime + tooling |
| Blender node parity | authoring validation | offline only |

## Runtime dependency order
1. Tiny UI host and synchronous shell.
2. Native renderer and core geometry/material doorway.
3. Deterministic fixed-step gameplay.
4. Shared-core frame evidence and quality policy.
5. Decorative visibility.
6. Material/texture hydration and cache evidence.
7. Ecology and LOD.
8. Recipe-driven world forms.
9. Bounded realtime realism.
10. Rigging/animation/IK embodiment.

## Public API philosophy
A public Ohrfront subsystem should accept a small record, provide one narrow capability, and preserve a stable facade even when its implementation becomes deeper. Advanced options belong in constructor/config records; the common path remains short.

## Diagnostics philosophy
Player HUD remains sparse. Core internals such as render pressure, cache statistics, visibility counts, recipe hashes, and ecology tier belong behind an explicitly opened ADVANCED disclosure or debug surface.

## Compatibility
If shared-core generic behavior must change, Mitzvah World compatibility facades and relevant shared tests must run before that change is considered stable.
