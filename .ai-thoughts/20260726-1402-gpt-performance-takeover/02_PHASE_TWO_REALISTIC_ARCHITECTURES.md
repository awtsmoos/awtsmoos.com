# Phase Two — Realistic Architecture Options

Boruch Hashem. Blessed is He. The Awtsmoos gives measure to motion; Awtsmoos.com needs fewer hops, never fewer safeguards.

## Architecture A — Minimal cache layer

Cache topology, capability, and session status briefly. Lowest change risk, but may leave browser lifecycle duplication.

## Architecture B — Shared lifecycle owners

Add bounded singleton owners for topology, browser connection, authenticated host controller, and topic socket. Stronger latency gains, higher invalidation complexity.

## Architecture C — Request pipeline coordinator

Introduce a stage coordinator with deduplication, timeouts, cancellation, progress events, and lifecycle release. Best observability and predictability, but requires careful compatibility adapters.

## Architecture D — Extension-first direct bridge

Cache extension availability and invoke the visitor relay directly after harmless topology discovery. Essential for public privacy boundary; must fail quickly when missing.

## Architecture E — Background automation migration

Keep pure packet compatibility while routing sends through `/direct-chat` and opaque `BH_DIRECT_` continuation keys. Necessary to remove old bearer/session paths.

## Working selection

Combine A, B, C, D, and E only where file inspection proves duplication. Preserve explicit modes, use short TTLs and lifecycle invalidation, and avoid caching all forbidden secret or upstream identifier material.
